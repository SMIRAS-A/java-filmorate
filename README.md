# Filmorate

Бэкенд сервиса оценки фильмов. Пользователи ведут каталог фильмов, ставят лайки и добавляют друг друга в друзья, а сервис отдаёт подборку самых популярных фильмов и список общих друзей.

Проект интересен не столько функциональностью, сколько тем, что вокруг неё: спроектированная с нуля схема базы данных, рукописный SQL вместо ORM и слой доступа к данным, спрятанный за интерфейсами, — благодаря чему хранение в памяти удалось заменить на СУБД, не тронув бизнес-логику.

## Стек

Java 21 · Spring Boot 3.2.4 · Spring Web · Spring JDBC (`JdbcTemplate`) · H2 · Maven · Lombok · JUnit 5 · Logbook · Checkstyle

ORM здесь нет намеренно: все запросы написаны руками, чтобы разобраться в том, что обычно скрывает Hibernate.

## Запуск

Требуется JDK 21.

```bash
mvn clean package
java -jar target/filmorate-0.0.1-SNAPSHOT.jar
```

Приложение поднимется на `http://localhost:8080`.

База — H2 в файловом режиме, каталог `./db` создаётся автоматически при первом запуске. Схема разворачивается из [`schema.sql`](src/main/resources/schema.sql), справочники жанров, рейтингов MPA и статусов дружбы наполняются из [`data.sql`](src/main/resources/data.sql) через `MERGE`, поэтому повторный запуск не плодит дубликаты.

Запуск тестов:

```bash
mvn test
```

## Валидация

Проверки собраны в отдельном классе `ModelValidator`, а не размазаны по контроллерам:

* название фильма не пустое, описание не длиннее 200 символов, продолжительность положительная, рейтинг MPA обязателен;
* **дата релиза не раньше 28 декабря 1895 года** — дня первого публичного киносеанса;
* у пользователя обязательны корректная почта и логин, а если имя не указано, вместо него подставляется логин.

Нарушение возвращает `400`, отсутствующий объект — `404`; формат ответа единый, собирается в `ErrorHandler`.

## Архитектура

```
controller → service → storage (интерфейс) → *DbStorage (JdbcTemplate)
```

Ключевое решение — **интерфейсы хранилищ** (`FilmStorage`, `UserStorage`, `GenreStorage`, `MpaStorage`). Сервисный слой знает только про них и ничего не знает про SQL. В первой версии проекта данные лежали в коллекциях в памяти; при переходе на базу поменялись только реализации, а сервисы и контроллеры остались нетронутыми.

## Схема базы данных

| Таблица | Назначение |
|---|---|
| `users` | пользователи: почта, логин, имя, дата рождения |
| `films` | фильмы: название, описание, дата релиза, продолжительность, ссылка на рейтинг |
| `mpa` | справочник возрастных рейтингов |
| `genres` | справочник жанров |
| `film_genres` | связь фильмов и жанров |
| `film_likes` | лайки пользователей фильмам |
| `friendship_status` | справочник статусов дружбы |
| `friendships` | связи дружбы между пользователями |

### Почему схема такая

**Рейтинг MPA вынесен в отдельную таблицу**, потому что это ограниченный набор фиксированных значений — держать его строкой в `films` значило бы хранить одно и то же слово тысячи раз и допускать опечатки.

**Жанры вынесены отдельно и связаны через `film_genres`**: у одного фильма может быть несколько жанров, а один жанр встречается у многих фильмов — это связь «многие ко многим», и без промежуточной таблицы она не выражается.

**Лайки** — тоже «многие ко многим»: пользователь лайкает много фильмов, фильм собирает лайки многих пользователей. Отсюда таблица `film_likes`.

**Дружба** хранится в `friendships` как пара пользователей плюс статус:

* заявка в друзья создаёт запись со статусом `UNCONFIRMED`;
* подтверждённая дружба хранится **двумя записями** со статусом `CONFIRMED` — по одной в каждую сторону.

Дублирование здесь сознательное: оно превращает поиск друзей и общих друзей в простой запрос по одному полю, без объединения выборок в обе стороны. Мы платим лишней строкой за то, чтобы не платить сложностью в каждом запросе.

## Примеры запросов

Получить топ N популярных фильмов:

```sql
SELECT f.film_id,
       f.name,
       COUNT(fl.user_id) AS likes_count
FROM films AS f
LEFT JOIN film_likes AS fl ON f.film_id = fl.film_id
GROUP BY f.film_id, f.name
ORDER BY likes_count DESC
LIMIT ?;
```

Получить подтверждённых друзей пользователя:

```sql
SELECT u.user_id,
       u.email,
       u.login,
       u.name,
       u.birthday
FROM users AS u
WHERE u.user_id IN (SELECT f.friend_id
                    FROM friendships AS f
                    INNER JOIN friendship_status AS fs ON f.status_id = fs.status_id
                    WHERE f.user_id = ?
                      AND fs.name = 'CONFIRMED');
```

Получить фильм вместе с названием рейтинга:

```sql
SELECT f.film_id,
       f.name,
       f.description,
       f.release_date,
       f.duration,
       m.name AS mpa_name
FROM films AS f
LEFT JOIN mpa AS m ON f.mpa_id = m.mpa_id
WHERE f.film_id = ?;
```

## Тесты

```bash
mvn test
```

Тесты покрывают два уровня: `ModelValidatorTest` — правила валидации, включая граничные случаи вроде даты релиза ровно в день рождения кинематографа; `FilmDbStorageTest` и `UserDbStorageTest` — слой доступа к данным на реальной базе, то есть проверяется не только Java-код, но и сами SQL-запросы.

## Выводы

**Схему стоит проектировать до кода.** ER-диаграмма, нарисованная в начале, сняла почти все вопросы к структуре запросов позже: когда связи продуманы, SQL пишется почти механически.

**Интерфейс между сервисом и хранилищем окупается сразу.** Замена хранения в памяти на СУБД не потребовала правок ни в контроллерах, ни в сервисах — только новых реализаций. Это самый наглядный урок проекта: граница, проведённая заранее, стоит дёшево, а проведённая задним числом — дорого.

**Рукописный SQL многому учит.** Ручные `JOIN`, агрегация лайков и выборка общих друзей показали, что именно ORM обычно делает за разработчика — и почему сгенерированный запрос иногда оказывается неожиданно тяжёлым.

**Денормализация — это осознанный размен, а не ошибка.** Две записи на одну подтверждённую дружбу выглядят избыточно ровно до того момента, пока не напишешь запрос общих друзей для симметричного варианта.
